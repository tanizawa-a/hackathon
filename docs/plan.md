# ニコザップ（nico-zap） デモ実装計画書

## 1. 目的とスコープ

ドワンゴ主催のハッカソンで「ランキング上位の動画を同時に浴び、盛り上がりを手がかりに見たいものへズームする」体験を見せるためのデモを、約4時間で作る。

- 形態：ブラウザで動く単体のWebアプリ（PC・フルHD想定）
- 動画一覧：スナップショット検索API v2から事前取得した実データ（3章参照）。取得できない場合はモックに切り替える
- 動画再生：モック（ローカルに置いた動画ファイル）
- コメント：モック（生成したタイムライン）
- ズーム時の要約：あらかじめ用意した固定文
- 対象外：ログイン、コメント投稿、本物のニコニコ動画の再生、スマホ対応、AIによる要約生成

## 2. 調査結果（2026年10月時点）

| 項目 | 状況 | デモでの扱い |
| --- | --- | --- |
| 動画の検索・一覧 | 公式の「スナップショット検索API v2」が公開されている。データは1日1回（AM5:00時点）更新。再生数・コメント数・いいね数・サムネイルURL・再生時間などを取得でき、再生数順などで並べられる | 事前取得して利用（3章） |
| 動画の再生 | 埋め込みプレイヤーをJavaScriptで操作する方法は、非公式のリファレンスのみ。プレミアム限定・有料動画は表示不可 | 使わない。ローカル動画で代替 |
| コメントの取得 | 公開APIなし。現行の取得手順は非公式 | 使わない。モックで代替 |
| 特許 | コメントのリアルタイム取得・描画・投稿の一連を実装すると、ニコニコの特許に触れる可能性がある旨の注意喚起が、第三者のコメント描画ライブラリにある | 動画上にコメントを流す表示はしない。コメントは枠外の帯に表示する |

参考：
- スナップショット検索API v2 ガイド：https://site.nicovideo.jp/search-api-docs/snapshot
- 埋め込みプレイヤーAPI非公式リファレンス：https://zenn.dev/xpadev/articles/8f742c8f8ce3d0
- niconicomments（注意書き）：https://www.npmjs.com/package/@xpadev-net/niconicomments

## 3. スナップショット検索APIの使い方

ドワンゴ主催のハッカソンであり、事業もドワンゴとして行う前提のため、API利用規約上の営利目的の制限は問題にしない。運用面では次を守る。

- ブラウザから直接呼ばず、開発開始時にスクリプトで1回だけ取得し、JSONに保存する（API負荷の抑制、デモ当日のオフライン動作、CORSの可否を気にしなくてよいため）。
- User-Agentにアプリ名を指定し、_contextも付ける。
- 取得条件の例：q=（キーワードなし）、filters[startTime][gte]=直近7日、filters[commentCounter][gte]=1000、_sort=-commentCounter、_limit=10。キーワードなし検索は負荷が高いため、filtersでヒット件数を10万件以内に絞る。
- 取得フィールド：contentId, title, viewCounter, commentCounter, likeCounter, lengthSeconds, thumbnailUrl, startTime。
- データは前日AM5:00時点のもので、ニコニコ動画の公式ランキングとは一致しない。デモでは「コメント数上位」と表示する。

## 4. 技術構成

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| ビルド | Vite | 立ち上げが速い |
| 言語 | TypeScript | データモデルを型で固定できる |
| UI | React | 枠の状態管理が多いため |
| スタイル | CSSファイル（CSS Grid） | 3×3のレイアウトをそのまま書ける |
| 動画 | HTML5 video要素 | playbackRate、muted、currentTimeを直接制御できる |
| 音声 | Web Audio API（StereoPannerNode） | 主役と脇役の定位を変える（任意機能） |
| モック動画の生成 | ffmpeg | 解像度違いの動画を一括生成する |
| データ取得（任意） | Node.jsスクリプト | 規約確認後に一覧JSONを作る |

## 6. データモデル

```ts
// src/types.ts
export type VideoKind = "video" | "live";

export interface VideoItem {
  id: string;              // mock01 / sm9 など
  title: string;
  kind: VideoKind;
  rank: number;            // 1〜10
  lengthSeconds: number;   // 生放送は放送枠の長さ
  viewCounter: number;
  commentCounter: number;
  thumbnail: string;       // モックはローカル画像
  sources: Record<Quality, string>; // 画質ごとの動画ファイル
}

export type Quality = "240p" | "360p" | "720p";

export interface CommentEvent {
  t: number;               // 動画内の秒（生放送は放送開始からの秒）
  text: string;
}

export interface Summary {
  videoId: string;
  from: number;            // 対象区間の開始秒
  to: number;              // 対象区間の終了秒
  oneLine: string;         // 「今は〇〇の話」
  recap: string;           // ここまでのあらすじ
}

export interface Peak {
  t: number;               // 山の中心の秒
  score: number;           // 通常ペースとの比
}
```

## 7. 機能と実装方針

### 7.1 グリッドと待機枠

- 3×3の9枠に、ランキング1〜9位を配置する。10位は待機枠として画面外のキューに置く。
- 枠の位置は固定し、入れ替え時も他の枠は動かさない。
- 枠の再生が終わったら、待機中の動画がその枠に入り、元の動画はキューの末尾に戻る。
- 9枠が一斉に入れ替わらないよう、各枠の開始位置を少しずつずらす。

### 7.2 ハイライト再生（盛り上がり場面だけ流す）

- 動画モードの枠は、頭から流さず、事前計算した山（Peak）の前15秒から30秒間だけ再生する。
- 30秒経過したら次の山へ移るか、山が残っていなければ待機枠と入れ替える。
- 設定で「頭から通常再生」に切り替えられるようにする。

### 7.3 盛り上がり検知

動画モード（事前計算）：
1. コメントを1秒ごとの件数に集計する。
2. 5秒の移動平均をとる。
3. 動画全体の中央値を「通常ペース」とする。
4. 移動平均が中央値の3倍を超えた区間を山とし、区間内の最大点を山の中心にする。
5. 山同士が20秒以内なら1つにまとめる。

生放送モード（逐次計算）：
1. 直近60秒の件数の指数移動平均を「通常ペース」とする。
2. 直近5秒の件数が通常ペースの3倍を超えたら、枠を光らせる。
3. 光らせたら20秒間は再判定しない（点滅し続けないため）。

しきい値はconfig.tsで調整できるようにする。

### 7.4 ズーム

- 枠をクリックすると、その動画を画面中央に大きく表示し、他の枠は一時停止する。
- ズーム中は720p・1倍速・音ありにする。
- 再生位置を10秒戻してから再生する。
- 閉じると、元の枠に戻り、他の枠の再生を再開する。

### 7.5 キャッチアップ（ズーム時）

軽い順に表示する。

1. 10秒巻き戻し（7.4）
2. 直近のコメントを最大10件、帯で表示する（CommentStrip）
3. 現在の再生位置に最も近い、過去の山の1行要約（summaries.jsonのoneLine）
4. （今回は作らない）「ここまでのあらすじ」ボタン

要約は、再生位置より後の区間を表示しない（ネタバレ防止）。

### 7.6 生放送モード

- 9枠のうち2枠を生放送として扱う（モック）。
- 生放送の枠は、停止中も擬似時計（liveClock）が進み続け、その間のコメントを蓄積する。
- 復帰時（ズームしたとき、ズームから戻ったとき）は、「見ていない間の要約」として、蓄積区間に対応する固定文と、その間の山の時刻一覧を表示する。
- 倍速は無効にする。

### 7.7 画質予算

- 総量 = 画素数 × フレームレート × 倍速 × 本数 を、設定した予算以下に収める。
- 予算を超える場合は、脇役の画質を1段ずつ下げる（360p → 240p）。
- 主役（ズーム中）は予算の対象外とし、720pで固定する。
- 画面右上に、現在の総量と予算をデバッグ表示できるようにする（審査で負荷の考え方を説明するため）。

### 7.8 音声（任意）

- 既定は、ズーム中の1本だけ音あり、他はミュート。
- 任意機能として、2本を左右に振り分けるモードを用意する（StereoPannerNodeで左右に定位）。

### 7.9 操作バー

- 「一斉に再生」開始ボタン
- 倍速（1倍・1.5倍・2倍）
- ハイライト再生のオン・オフ
- 終了時の動作（消す／次を自動再生）
- デバッグ表示のオン・オフ（余裕があれば）

## 8. モックデータの作り方

### 8.1 動画

ffmpegのテストパターンで、10本 × 2画質（360p・720p）を生成する。240pは時間があれば追加する。タイトルと経過時間を映像に焼き込み、どの動画か一目で分かるようにする。

```bash
# scripts/generate-videos.sh（概略）
for i in $(seq -w 1 10); do
  for q in 360 720; do
    w=$((q * 16 / 9))
    ffmpeg -y -f lavfi -i "testsrc2=size=${w}x${q}:rate=30:duration=180" \
      -f lavfi -i "sine=frequency=$((200 + 10#$i * 40)):duration=180" \
      -vf "drawtext=text='MOCK ${i}  %{pts\:hms}':fontsize=$((q / 10)):fontcolor=white:x=10:y=10" \
      -c:v libx264 -pix_fmt yuv420p -c:a aac -shortest \
      "public/videos/mock${i}_${q}p.mp4"
  done
done
```

- 長さは3分程度にし、ファイルサイズを抑える。
- 手持ちの自作動画などに差し替えられるよう、ファイル名の規則だけ守ればよい作りにする。
- drawtextに使うフォントは環境ごとに確認する。

### 8.2 コメント

- 動画ごとに、通常ペース（毎秒0.5〜2件）に加えて、2〜4個の山（毎秒10〜20件、10〜20秒間）を持つタイムラインを生成する。
- コメント本文は、定型の短文リスト（例：「きたああ」「ここすき」「草」「8888」）から選ぶ。
- 実在のユーザー名や実在のコメントは使わない。
- 乱数のシードを固定し、毎回同じデータになるようにする（デモの再現性のため）。

### 8.3 要約

- 時間短縮のため、動画ごとに区間を分けず、山ごとに1行要約を1つだけ用意する（10本 × 2〜4件）。あらすじは省略する。
- 生放送の2本は、「見ていない間の要約」用の文を2〜3パターン用意し、復帰時にローテーションで表示する。
- 文面は生成AIに下書きさせ、目視で整える。

### 8.4 一覧

- fetch-ranking.tsで、3章の条件で10本を取得し、ranking.jsonに保存する。
- 実データのタイトル・サムネイル・再生数・コメント数を表示し、再生する映像はモック動画を1対1で割り当てる。
- APIが取得できなかった場合に備え、架空タイトルのranking.jsonも用意しておく。

## 9. 当日のデモシナリオ（約3分）

1. 「一斉に再生」を押し、9枠が同時に動き出す。
2. 2倍速に切り替え、数秒眺める。
3. ある枠が光る。クリックしてズームし、10秒前から再生、コメント帯と1行要約が出る。
4. 戻ると他の枠が再開する。
5. 1つの枠が終わり、10位の動画が自動で入ってくる。
6. 生放送の枠をズームし、「見ていない間の要約」を見せる。
7. デバッグ表示をオンにして、画質予算の考え方を説明する。

## 10. タイムライン（約4時間）

データ準備（スクリプト）と画面実装は並行できるため、作業を2レーンに分ける。1人で進める場合は、データ準備を最初の30分で済ませる。

| 時間 | レーンA：画面 | レーンB：データ | 完了の目安 |
| --- | --- | --- | --- |
| 0:00〜0:20 | Vite＋React＋TSの雛形、types.ts、config.ts | API取得スクリプト実行、ranking.json保存 | 雛形が起動し、実データ10本が揃う |
| 0:20〜1:00 | Grid・Tile、9本の同時再生、倍速、ミュート | モック動画とコメントの生成 | 9本が2倍速で同時に動く |
| 1:00〜1:40 | 盛り上がり検知（事前計算）と枠の発光 | 1行要約の文面作成 | 山の時刻で枠が光る |
| 1:40〜2:20 | ズーム、他枠の停止、10秒巻き戻し、コメント帯、1行要約 | ― | ズーム時に手がかりが出る |
| 2:20〜3:00 | 待機枠と自動入れ替え、生放送モード（簡易版） | ― | 10位が入ってくる。生放送枠で復帰時の要約が出る |
| 3:00〜3:30 | 余裕があれば：画質予算のデバッグ表示、ハイライト再生 | ― | ― |
| 3:30〜4:00 | デモ通し、しきい値調整、見た目の仕上げ | ― | シナリオが通しで動く |

生放送モードの簡易版：停止中に経過した秒数だけを記録し、復帰時に「見ていない間：◯分◯秒」と用意した要約文、その間の山の時刻を表示する。コメントの逐次検知は省略し、生放送枠も事前計算の山で光らせる。

## 11. 優先順位

時間が足りない場合は、下から削る。3:00の時点で「必須」が終わっていなければ、「重要」以降には手を付けない。

- 必須：3×3同時再生、倍速、盛り上がりの発光、ズームと他枠停止、10秒巻き戻し、コメント帯、実データの一覧表示
- 重要：1行要約、待機枠の自動入れ替え、生放送モード（簡易版）
- 余裕があれば：画質予算のデバッグ表示、ハイライト再生
- 今回は作らない：あらすじ、休憩タイマー（スライドで説明する）、左右の音声振り分け、生放送の逐次検知、240p

## 12. リスクと対策

| リスク | 対策 |
| --- | --- |
| 9本同時のデコードで、デモ用PCが重くなる | 脇役を240pに落とす設定を用意する。前日にデモ用PCで実測する |
| ブラウザの自動再生制限で動画が始まらない | 全枠をミュートで開始し、開始ボタンのクリックを起点に再生する |
| 盛り上がりのしきい値が合わず、光りすぎる／光らない | config.tsで調整可能にし、通し確認の時間で詰める |
| APIが取得できない（メンテナンス、エラー） | 架空タイトルのranking.jsonに切り替える |
| 4時間で終わらない | 11章の順に削る。3:00時点で判断する |
| 特許への抵触 | 動画上にコメントを流さない。コメント投稿機能を作らない |
| 当日のネットワーク不調 | すべてのデータをローカルに置き、オフラインで動くようにする |

## 13. 確認事項

1. 作業は1人か、複数人か（10章のレーン分けの要否）。
2. デモ用PCのスペック（デコード負荷の確認のため）。
3. 審査で画面を投影するか、手元の画面を見せるか（解像度とレイアウトの調整のため）。
4. モック動画を、テストパターンではなく見栄えのする素材（自作の映像など）に差し替えるか。
5. 開発環境にffmpegとNode.jsが入っているか。
